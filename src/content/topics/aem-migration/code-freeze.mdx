<p class="sec-note">With cutover by business case, AEM stays in production for most of the programme. A full code freeze for that long would stop the business, so the question is which kinds of change AEM still takes.</p>

<p>Globant's recommendation is that AEM takes no new functionality from the moment the migration scope is signed off: the close of discovery, when EG agrees the disposition log. Before that the inventory is still being taken; after it, anything added to AEM was never assessed against the target model. Whether the business can live with that is EG's decision.</p>

<div class="decide risk">
  <h4><span class="stamp">cost</span>Parity means building twice</h4>
  <p>If AEM keeps taking new functionality after the migration scope is signed off, every feature is built on AEM and then built again on the new stack. It also reopens the disposition log, because the new components were never assessed against the target model, and it moves the target the migration is aiming at.</p>
  <p>Parity is possible. It is a budget line rather than a default, and every case needs EG's agreement.</p>
</div>

<h3>Non-parity enhancements during coexistence</h3>
<p>Adding the non-parity enhancements to AEM, its header and footer included, would be new functionality on a platform being retired, so it is not done. The enhancements arrive business case by business case, and during coexistence visitors can see both versions of the site (D-30). This holds as long as the enhancements have no fixed public launch date that falls before the last business case reaches 100%.</p>
