00Seven places where the document argues with itself

These aren't nitpicks. Each one moves the content model, the integration pattern, or the effort by a meaningful amount, and each one has to be settled before a credible estimate exists.

WhereThe conflictWhy it matters
Pilot parameters ↔ CMS-10 Scale note anticipates a unique proof point per partner at ~1M partner records, while CMS-10 models the proof-point value as a typed field inside the Contentful entry. Those are different systems: one is a template with a value injected at render time, the other is a per-partner entry. Decides entry volume, content model, licensing tier, and whether Contentful is even in the per-recipient path.
Parameters ↔ CMS-31/38/37 "NBA does the deciding — not Contentful" sits next to pass criteria that read "the correct variant resolves for a given segment/tone" and a variant + locale resolution order. Meanwhile CMS-37 (variant-to-audience mapping) is marked out of scope. Either channels fetch a fully-resolved ID, or they fetch base ID + parameters and Contentful resolves. Different API contract, different pilot.
Flow step 5 ↔ step 6 Step 5: all channels fetch the same content ID. Step 6: the same base ID, but a channel-specific variant of every proof point should be possible. One lookup key versus a composite key shared across NBA, SFMC and CRM/VMC.
Pilot parameters ↔ CMS-06/18/39 No email is sent and no CRM/VMC view is built — yet the pass criteria say the proof point "renders with the same wording", that RTL layout is previewed, and that content ID is recorded on a send/render event. Without a rendering target, these are unverifiable. The evidence artifact has to be agreed up front.
Web-specific table CMS-22 (DAM), CMS-23 (renditions) and CMS-24 (visual authoring) are marked "Yes — in this pilot", but the How column for each says the opposite ("no images are part of this pilot's test content"), and all three Pass Results read "To be confirmed" — while UC2 is entirely about images and video. Three capabilities with no pass criteria, in or out depending on which column you read.
Step 5 ↔ step 6 ↔ CMS-01 Step 5 has the CRM showing the Market Manager the same tone of voice the partner already received — tone persisting across channels. Step 6 and CMS-01 then describe a channel-specific variant and channel-specific content models, which makes channel read as a peer of tone and segment. Tone and channel end up sounding like the same dimension. They are opposites: tone is chosen per partner and must stay constant across surfaces, channel is fixed per surface and identical for every partner.
Capability list Stated as "46 capabilities in total (numbered CMS-01 through CMS-47)". CMS-01→CMS-47 is 47 numbers, and CMS-27 appears nowhere in the document. If the pilot is scored against a fixed list, a missing item is a missing requirement.

01Use case 1 — Cross-channel proof point consistency

Everything here is written from what the document states unambiguously. Where a story depends on one of the contradictions above, it's marked and the dependency is named in the acceptance criteria rather than assumed away.

Epic A — Content modelling and authoring

US-A1Channel-specific content models from one base entryCMS-01

As a content modeller, I want the proof point modelled as channel-specific renderings derived from a single base entry, so that email and CRM/Field each get the structure they need without the copy being written twice.

  • At least two channel renderings exist (Email, CRM/Field) for the same base entry.
  • The channel rendering is produced from the base entry plus channel parameters; every step still requiring manual authoring is listed.
  • Generated output is diffed against a hand-authored reference supplied by EG; differences are documented, not waved through.
  • The mechanism used (field-level conditions, referenced types, app) is documented with its limits.
US-A2Typed, validated proof-point valueCMS-10blocked: Q1

As a content author, I want the proof-point value held in a typed, validated field rather than free text, so that a malformed or out-of-range number is caught before publish.

  • The field is typed (numeric/date), not a string.
  • Locale-aware number formatting is applied per locale.
  • A malformed or out-of-range value is rejected or flagged by validation, never silently accepted.
  • Validation rules are configurable by an author without a code change.
  • Scope depends on Q1: if the value is injected at render time, this story applies to the template placeholder, not to a stored value.
US-A3Segment and tone taxonomy on every variantCMS-19

As NBA, I need each content variant to carry the segment and tone metadata my decisioning reads, so that I can select a variant without a human in the loop.

  • Every variant carries an NBS segment tag and a tone tag; both are selection criteria, not presentation.
  • Tags come from a controlled vocabulary, not free-text entry.
  • Tags are returned in the Delivery API response and are filterable by query.
  • NBA correctly filters and selects variants using those tags against the pilot content set.
  • Channel is not among the selection tags — it is supplied on the fetch and selects a rendering after the variant has been chosen (see US-A9).
US-A4Named variants on a single entryCMS-31blocked: Q2, Q23

As a content author, I want to author multiple named variants on top of a mandatory default entry, so that segment and tone variations live on one entry rather than as separate duplicated entries.

  • One entry carries a mandatory default plus at least two named variants.
  • A new variant can be added without altering the content type.
  • For a given segment + tone, exactly one variant is returned, deterministically. Channel plays no part in that resolution.
  • The document records which system performed the resolution (Contentful or NBA) — see Q2.
US-A5Shared proof-point block reused across surfacesCMS-42

As a content author, I want the proof-point block referenced by each surface rather than copied into it, so that one edit reaches every channel.

  • Email and CRM/Field reference the same block; no duplicate is created.
  • An edit to the block is reflected in both surfaces without re-authoring.
  • A where-used view shows every surface consuming the block.
US-A6Inventory and coverage view across variants and localesCMS-20

As a content operations owner, I want a view of entry × variant × locale with lifecycle status, so that I can see which combinations have bespoke copy and which fall back to default.

  • The view lists every segment/locale combination with its status.
  • Custom variant versus default fallback is distinguishable at a glance.
  • The view is exportable.
US-A7Authoring and retagging with no developer involvementtest goal

As an EG content author, I want to create, update, retag and republish content entirely in the UI, so that routine changes don't queue behind an engineering release.

  • An EG author (not the delivery team) completes the full cycle unaided.
  • No deployment or code change is required.
  • Adding one new field and one new tag dimension is performed live; effort, role required and any code impact are recorded.
US-A8Metric composed inside a localised sentenceCMS-47blocked: Q5

As a partner, I want the number to read naturally inside the sentence in my language, so that the message doesn't read like a template with a value dropped into it.

  • Plural/singular, gender inflection, word order and ordinals are correct in each of the five locales.
  • A native reviewer per locale signs off on the composed output.
  • The composition mechanism and where it executes (CMS, channel, or intermediate service) is documented.
US-A9Channel rendering carries its own register and audienceCMS-01CMS-19

As a content author, I want each channel rendering to declare who it addresses and in what register, so that an email speaking to a partner and a CRM card briefing a Market Manager are not written as if they were the same thing.

  • Every channel rendering carries an audience value of partner or internal, and a register appropriate to that surface.
  • The partner-facing tone selected by NBA is preserved across every channel rendering of the same variant; the register changes with the surface, the tone does not.
  • Register and audience are declared on the rendering and never on the variant, so they cannot be mistaken for selection criteria.
  • Generation prompts and review criteria differ by audience — a briefing for an internal user is reviewed against different standards from copy sent to a partner.

04Build versus configure

Every story classified by what it actually takes to satisfy it. Five buckets rather than two, because a straight development/configuration split hides the two things that matter most here: capabilities that are configuration only if the right licence is in place, and capabilities where the CMS side is trivial but all the work sits in a system that isn't Contentful.

Six places where "out of the box" quietly isn't

  1. An ID per entry + variant + locale + version (US-C1). Contentful issues an ID per entry. Locale is a query parameter, version is a revision counter, and variant isn't a core concept at all. The identifier the whole use case depends on has to be defined as a composite key and built — it isn't handed to us.
  2. Independent publishing per locale (US-B1). Publishing acts on the entry, and all locales go together. "A pending translation doesn't block another locale" needs either entry-per-locale modelling or a release-based workaround, both of which change the content model.
  3. Named variants on one entry (US-A4). Core entries have no variant dimension. This is either the personalisation add-on or hand-modelled as referenced entries with tags — and the second option is what makes CMS-45's variant-explosion concern real.
  4. Channel rendering generated from a base entry (US-A1). There is no "clone this entry per channel parameter" behaviour to configure. Field-level conditions, a custom app, or a transform in the delivery layer — all of them code.
  5. Locale-aware number formatting and sentence composition (US-A2, US-A8). The CMS stores strings and validates them. Plural, gender, ordinal and word-order handling executes in whatever renders the message. If EG wants a composed sentence returned from the API, that implies a service between Contentful and the channel.
  6. Coverage view by segment and locale (US-A6). The entry list filters by status and content type, not by which segment/locale combinations have bespoke copy. That view is a custom app or a scheduled export.

What the split says about the pilot

Twelve stories are pure configuration and three more become configuration with the right licence — so the CMS evaluation proper is a small piece of work. The remaining twenty-four are development, and thirteen of those sit outside Contentful entirely, in SFMC, CRM/VMC, NBA and a UC2 front end. Read together with the parameters that rule out development from the NBA, VMC and Salesforce teams, the pilot as scoped is largely an integration project with a CMS evaluation inside it. That's worth saying out loud early, because it decides who staffs it and who is accountable when a capability can't be demonstrated.

05Open questions for EG

Ordered by how much the answer changes the shape of the work. The first six are the ones I'd want closed before quoting anything.

Architecture — answer these before estimating

Q1

Where does the personalised value actually live?blocking

Is the proof-point value stored in Contentful per partner, or does Contentful hold a templated sentence with the value injected at render time from NBA or an SFMC data extension?

CMS-10 describes a typed value field in the entry; the scale note anticipates a unique proof point across ~1M partner records. Those can't both be true in the same design. The answer sets the entry count, the content model, the licensing tier and whether Contentful sits in the per-recipient path at all.
Q2

Who resolves the variant — NBA or Contentful?blocking

Do the channels fetch a fully-resolved variant ID that NBA has already chosen, or a base ID plus segment/locale parameters that Contentful resolves on the way out?

The parameters say NBA decides and mark CMS-37 out of scope, but CMS-31 and CMS-38 are scored on content "resolving" for a segment/tone combination. If Contentful resolves, audience mapping is in scope and the pilot is larger than described. Segment and tone are the only inputs to that resolution; channel is not one, and Q6b settles why.
Q3

One content ID across channels, or one per channel rendering?blocking

Step 5 says every channel fetches the same ID; step 6 says a channel-specific variant of every proof point should be possible under the same base ID. Is the shared contract base_id, or base_id + channel?

It determines what NBA hands off, what SFMC and CRM store on their records, and what "the same ID everywhere" is actually being proved.
Q4

What mechanism produces the channel-specific rendering automatically?blocking

CMS-01 passes only if the channel rendering is generated from one base entry plus channel parameters. What is the expected mechanism, and what hand-authored reference will the output be compared against?

There's no native "clone this entry by channel parameter" behaviour to point at. This becomes field-level conditions, referenced content types, or a custom app — each with different effort and different governance.
Q5

Where is the localised sentence assembled?blocking

Should the API return a fully composed localised sentence with the metric inside it, or the message pattern plus parameters for the channel to compose?

CMS-47 is the capability the document calls out as a genuine capability gain, not just efficiency. Plural, gender and ordinal handling normally resolves in the renderer, not the store — so if EG expects a composed sentence back, something has to inject and translate at request time, and that is a design decision, not a configuration one.
Q6

How does SFMC fetch at send time?blocking

Per-recipient outbound calls from SFMC at send time, or a data extension hydrated before the send? Which SFMC modules are in play — Content Builder, Journey Builder — and are outbound calls permitted under EG's SFMC configuration?

Per-recipient external calls at send time carry hard platform limits and are the usual failure point in this pattern at volume. Worth settling now rather than discovering it in the pilot.

Scope boundaries

Q6b

Is tone a property of the partner or of the channel?blocking

Step 5 has the CRM continuing the conversation in the same tone of voice the partner already received, which makes tone a partner attribute that persists across surfaces. CMS-01's "channel-specific content models" and step 6's "channel-specific variant" pull the other way. Which is it?

If tone belongs to the partner, it is a selection criterion alongside segment and channel is only a rendering parameter. If tone belongs to the channel, CMS-19 loses half its pass condition because tone stops being decisioning metadata, CMS-31 collapses to segment alone, and CMS-06 becomes trivially satisfiable since no cross-channel constant remains. Three capability results move on this one answer.
Q7

Are UC1 and UC2 one pilot or two tracks?

The capability matrix is written entirely from UC1's perspective and marks page-building capabilities as belonging to "the separate marketing-page CMS / replatform track" — while UC2, in the same document, is exactly that track. Same window, same team, same readout, or separate?

Q8

Who builds the rendering layer for UC2?

"Publish the page and it renders as designed" implies a front-end application, hosting, routing, CSS/JS and GTM wiring. Is EG providing an existing head to point at Contentful, or is building it part of the pilot?

This is the single largest effort variable in the document. A pilot that includes building a head is a different order of work from one that authors into an existing one.
Q9

Does the component library already exist, or does it have to be built?

The acceptance criteria say pages are authored from "pre-existing components or layouts" — pre-existing where? If it means the Figma library, the corresponding content types and components have to be built first. How many components does the library contain, and do the three pages stay inside it?

Q10

Where are the three pilot pages published?

Target environment, domain and CDN. I'm assuming not live partner.expediagroup.com, but that needs confirming along with who owns the DNS and certificate work if it's a new host.

Q11

What is the current-state CMS, and is coexistence in scope?

The document offers current-state technical specifications and a site index "for reference", and marks migration tooling (CMS-30) as demo-only. Is any coexistence or content migration expected during the pilot, or purely greenfield pages?

Q12

Are CMS-22, CMS-23 and CMS-24 in the pilot?

All three are marked "Yes", their How column argues the opposite, and all three Pass Results read "To be confirmed". Given UC2 uses images and video, I'd propose scoping them to UC2 and writing pass criteria accordingly — confirm.

Q13

Is CMS-27 intentionally excluded?

The list is described as 46 capabilities numbered CMS-01 through CMS-47. CMS-27 doesn't appear anywhere in the document. Deliberate, or an omission?

Q14

What counts as evidence when nothing is rendered?

No email is sent and no CRM/VMC view is built, yet CMS-06 is scored on "renders with the same wording", CMS-18 on RTL layout, and CMS-39 on a send/render event. What is the agreed artifact — a payload diff, an SFMC preview or seed send to an internal list, a static render harness?

Worth agreeing in writing. "Pattern matching" means different things to a content lead and to an engineer, and this is where a pass/fail argument would happen.
Q15

Who builds the feedback loop?

CMS-39, CMS-40 and CMS-41 are all marked in scope, but the flow description says reporting "is a separate detail we're not solving in this document" and the parameters rule out NBA development. Who builds and validates it, and against what?

Inputs and dependencies

Q16

Can we have the Travel Corridors payload spec and a sample?

CMS-46 requires the real payload, not a stub, while the parameters allow "minor tweaks" with no NBA development. Who makes the tweaks? Is there a sandbox endpoint, or will this be a static payload file?

Q17

How many variants, exactly?

"Multiple" and "enough real options that NBA is actually choosing between something" won't size the work. How many opportunity types × NBS segments × tone values — and separately, how many channel renderings per variant, since channel multiplies authoring and review volume without adding a selection dimension? Who authors the EN-US source copy and the tone guidelines?

Q18

Why do the two locale sets differ?

UC1 uses EN-US, Arabic, Thai, German and Japanese; UC2 uses EN-US, German, French, Japanese and Swedish. Intentional, or should one set align to the other? Is RTL relevant to the web pages too?

Q19

Contentful, Babel Prime, or both — and who builds the connector?

The document raises this itself. Extending it: does Babel Prime expose an API or a supported connector, and if the answer is "a mix", who owns building and maintaining that integration during the pilot?

Q20

Who owns the data contract, and by when?

Which SFMC and CRM/VMC identifiers tie a send or a view back to the same partner, who signs the contract, and what is the date? Also: are there masking rules for partner identifiers in a non-production pilot?

Q21

Which EG people are available, and for how long?

Several pass criteria can only be met by EG staff: an author for the no-developer-involvement test, a Market Manager or CRM owner for the ingest mapping, an SFMC engineer, and a native reviewer per locale for the sentence-composition sign-off.

Q22

Is the SFMC future-state environment ready within the pilot window?

The document is explicit that this pilots against future-state SFMC rather than Marketo. Is that instance provisioned and accessible, and has outbound connectivity to Contentful cleared security review?

Commercial and evaluation

Q23

Which Contentful tier and add-ons are assumed?

Several requested capabilities sit outside a base platform entitlement — scheduled publishing, workflows and tasks, multiple environments, SSO and RBAC, and in particular variant dimensions on an entry (CMS-31) and audience mapping (CMS-37), which are typically delivered by Contentful's personalisation product rather than core entries. What is licensed for the pilot?

If personalisation isn't licensed, CMS-31 gets modelled by hand and the variant-explosion concern in CMS-45 becomes real during the pilot rather than after it.
Q24

Is this a comparative evaluation against other CMS vendors?

The 46-capability list is described as "Expedia's consolidated CMS list". If other vendors are being assessed against it, are the pass criteria and evidence formats identical across vendors, and who scores?

Q25

What is the timeline and the definition of done?

Start, end, readout date, who signs pass or fail, and what happens to the pass criteria currently marked "to be confirmed" or "to be defined".

Q26

How is a demo-only capability weighted against a built one?

Roughly nineteen capabilities are assessed by demo or documentation. Do they score the same as capabilities proven in the build, and is a "documented but unproven" answer a pass?
