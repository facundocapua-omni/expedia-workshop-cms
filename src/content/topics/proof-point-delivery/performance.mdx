<p class="sec-note" data-origin="uc1:performance:0">The numbers below are engineering estimates of what the proposed design can absorb. EG's real send volumes, click-through rates and latency targets are open questions; until they arrive, these establish the order of magnitude rather than a commitment.</p>

<div class="decide" data-origin="uc1:performance:1">
  <h4>Why the burst is a caching problem and not a CMS problem</h4>
  <p>The number of <strong>distinct resolved payloads</strong> is variants × locales × channels × live versions — hundreds in the pilot, low hundreds of thousands at full production scale. It is not a function of the partner base. The only per-partner element is the parameter values, which arrive with the request and are substituted on the way out.</p>
  <p>So the content is near-perfectly cacheable, the working set fits in memory on a single node, and a send of any size generates reads against a cache rather than against Contentful. The delivery API is read on publish, never on request.</p>

<p data-origin="uc1:performance:3">The headline: even the aggressive burst case sits an order of magnitude below what a single instance handles, and the service is stateless so it scales horizontally anyway. The constraint that actually binds is the delivery API's published rate limits — which is precisely why it is kept off the request path.</p>

<h3>Under option B</h3>
<p>The numbers hold in <a href="#flow">option B</a>. The snapshot store gains a pointer per proof point, segment, tone, locale and channel to the latest published version, moved on every publish, so the content is as cacheable as before and a send still generates no Contentful reads. The trace is the same as in option A: a record per resolution, written to EG's log system off the request path.</p>
