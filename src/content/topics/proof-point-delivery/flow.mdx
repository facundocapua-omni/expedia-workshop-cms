<h3>Who selects the variant: two options for EG</h3>

<div>
  <p class="sec-note">Figure 3 and its table describe option A, where NBA chooses the variant. There is a second option: NBA sends the decision — which proof point, for which segment, in which tone — and the Content Resolution API serves the published variant written for it. Both keep the resolution layer, and in both Contentful decides nothing. They differ on who picks the variant and on which version a channel receives. EG chooses between them.</p>

<p class="cap">Figure 4 — Consumption flow under option B. Same numbering as Figure 3: interaction 3 is gone and 4 carries the decision. Solid arrows are synchronous requests; dashed are asynchronous.</p>

<p>Interactions 2, 9 and the trace are the same in both options. The others change:</p>
<ul class="tight">
  <li><strong>1</strong> moves the latest-version pointer for each proof point, segment and tone instead of refreshing an index.</li>
  <li><strong>3 goes away.</strong> NBA reads no variant index; it needs only the shared taxonomy.</li>
  <li><strong>4 carries the decision.</strong> Proof point, segment and tone travel in place of the content reference, with the same partner, locale and parameters.</li>
  <li><strong>5, 7 and 8 resolve when they fetch</strong>, to the latest published version. A channel that needs exactly what an earlier fetch returned sends the reference from that response.</li>
  <li><strong>6 returns the reference the resolver chose</strong>, where in option A it echoes the one NBA sent.</li>
</ul>
<p>Interaction 9 stays, and matters more: it is how NBA learns which variant its decision became.</p>

<h3>Option B in detail</h3>
<div>
  <Fragment set:html={optionB} />
  <ul class="tight">
    <li><strong>A reference wins.</strong> If the fetch carries <code>ref</code>, the resolver serves exactly that variant and version, as in option A. That is also how anyone replays what was sent.</li>
    <li><strong>Otherwise, the one variant written for the decision.</strong> The resolver looks up the published variant of the proof point for that segment and tone and serves its latest published version. Publishing a second variant for the same proof point, segment and tone is blocked at authoring, so the lookup never has to choose between two.</li>
    <li><strong>No such variant: the proof point's default copy.</strong> Reported as <code>selection: "default"</code>. No other variant is tried, so what goes out is either the copy written for this segment and tone or the approved generic copy, never a guess between them.</li>
    <li><strong>Missing translation: the variant in the source locale.</strong> Reported with <code>fallbackApplied</code>, as in option A. The partner gets the specific message in English rather than generic copy in their language.</li>
  </ul>
  <p>Nobody filters by channel before the fetch, so publishing also checks that every variant fits every channel profile, or carries an override for the one it does not fit.</p>
  <p>As in option A, every resolution writes one record to EG's log system, here with the decision in it: partner, channel, proof point, segment, tone, locale requested and served, the variant and version served or the default copy, and the <code>consistencyKey</code>. It is written off the request path. In this option the trace is the only answer to "what did this partner see, and where", because two surfaces can resolve the same decision to different versions. Channels still emit the served-variant event, and it becomes the only way NBA learns which variant its decision turned into.</p>
  <p>Option B is not the alternative where Contentful resolves segment and tone through a personalisation product (<a href="/ideas/uc1-solution-architecture/#resolution-layer">UC1, alternatives considered</a>). Here NBA still decides what to say and in which tone. The resolver only finds the copy written for that decision, with a lookup that gives the same answer every time for the same published content.</p>

</div>
