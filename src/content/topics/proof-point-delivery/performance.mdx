  <div class="decide">
    <h4>Why the burst is a caching problem and not a CMS problem</h4>
    <p>The number of <strong>distinct resolved payloads</strong> is variants × locales × channels × live versions — hundreds in the pilot, low hundreds of thousands at full production scale. It is not a function of the partner base. The only per-partner element is the parameter values, which arrive with the request and are substituted on the way out.</p>
    <p>So the content is near-perfectly cacheable, the working set fits in memory on a single node, and a send of any size generates reads against a cache rather than against Contentful. The delivery API is read on publish, never on request.</p>

  <p>The headline: even the aggressive burst case sits an order of magnitude below what a single instance handles, and the service is stateless so it scales horizontally anyway. The constraint that actually binds is the delivery API's published rate limits — which is precisely why it is kept off the request path.</p>

  <h3>Where the cache sits is a hosting decision, not a design one</h3>
  <p>The snapshot store is already an immutable key-value store addressed by variant, version, locale and channel. That makes it the primary read path and the cache at the same time — there is no separate cache to invalidate, because a published version never changes.</p>
