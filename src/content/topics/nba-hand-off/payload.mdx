    <h4><span class="stamp">D-01</span>Contentful stores the message template, never the partner's number</h4>
    <p>A proof point holds localised copy with <strong>named variables</strong>, declared once on the proof point — not <code>"seen 47 times"</code> but <code>"Your property page was seen \{views\} times in the last \{windowDays\} days"</code>. The value arrives with NBA's decision and is substituted at resolution time.</p>
    <p>This is what keeps the content set at variant scale — dozens of entries — instead of partner scale. No entry anywhere holds a partner identifier or a partner's metric.</p>
    <p>Grammatical agreement between the value and the sentence around it is <strong>out of scope for the POC</strong>. See the <a href="/ideas/uc1-solution-architecture/#resolution-layer">deferred-scope note in UC1</a>, because it is not a detail.</p>

  <div data-origin="uc1:position:3" class="decide">
    <h4><span class="stamp">D-03</span>One content reference everywhere; channel is a parameter, not a different ID</h4>
    <p>All channels quote the same reference. The channel is passed alongside it, and selects the channel profile that shapes what is returned. This makes both statements in the source document true at once: every surface is fetching the same content, and each surface gets copy shaped for it.</p>
    <p>It also gives the consistency test something to assert against — every response carries a <code>consistencyKey</code> derived from variant, version, locale and parameters, and identical keys across channels is a machine-checkable pass.</p>
  </div>

<h3>The content reference</h3>

  <p data-origin="uc1:ref:0" class="sec-note">The identifier the whole use case rests on. It does not exist natively — the platform issues an ID per entry, with locale as a query parameter and version as a revision counter — so it has to be defined as a contract and implemented.</p>

  <div data-origin="uc1:ref:1"><Fragment set:html={contentReference} /></div>

  <ul data-origin="uc1:ref:2" class="tight">
    <li><strong>The reference is opaque to channels and meaningful to us.</strong> SFMC passes it through without parsing; the resolution service decomposes it. Keeping it decomposable matters more than keeping it short — an opaque hash is untraceable at 2am.</li>
    <li><strong>Version is part of the identity, not metadata.</strong> Without it, a republished entry silently changes what a send delivers, and the traceability requirement ("given this ID, show me the exact content") becomes unanswerable for anything historical.</li>
    <li><strong>Locale and channel travel beside it, not inside it.</strong> That is what makes "the same content ID everywhere" literally true across channels, which is the claim the pilot is testing.</li>
    <li><strong>Parameters are the partner's data and never persist in the CMS.</strong> They exist in the decision payload and in the resolved response.</li>
  </ul>

<h3>Under option B</h3>
<p>In <a href="#variant-metadata">option B</a> NBA hands off the decision instead of a reference, and the reference comes back in the response. The rest of this topic holds: channel travels beside the decision, parameters never persist, and the reference — returned by the resolver and written to the trace — is what "given this ID, show me the exact content" is asked of. It is also what a channel sends when it needs exactly what an earlier fetch returned. Identical <code>consistencyKey</code> values across channels still pass the consistency test, unless a republish falls between two fetches.</p>
